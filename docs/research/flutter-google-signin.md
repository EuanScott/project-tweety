# Firebase / FlutterFire Google Sign-In Setup — Research for Issue #23

**Date checked:** 2026-09-09

Scope: primary sources only (firebase.google.com/docs, firebase.flutter.dev, pub.dev package/changelog pages, flutterfire_cli GitHub README, and the Android native client-auth doc that `firebase.google.com/docs/auth/android/google-signin` links to directly for fingerprint commands).

---

## 1. Recommended mechanism today

For **Flutter native apps (Android/iOS)**, the current documented pattern is still the credential-exchange flow, not `signInWithProvider`/`signInWithPopup`:

```dart
final GoogleSignInAccount? googleUser = await GoogleSignIn.instance.authenticate();
final GoogleSignInAuthentication googleAuth = googleUser.authentication;
final credential = GoogleAuthProvider.credential(idToken: googleAuth.idToken);
return await FirebaseAuth.instance.signInWithCredential(credential);
```

The doc states explicitly: *"On native platforms, a 3rd party library is required to trigger the authentication flow"* — i.e. `google_sign_in` is still required on Android/iOS; there is no native-platform `signInWithProvider` path for Google in the Flutter docs.

`signInWithPopup` (and by extension `signInWithProvider`'s redirect/popup family) is documented only for **web**:

```dart
GoogleAuthProvider googleProvider = GoogleAuthProvider();
return await FirebaseAuth.instance.signInWithPopup(googleProvider);
```

Cross-checking against the native Android Firebase doc (`firebase.google.com/docs/auth/android/google-signin`, non-Flutter): it now recommends **Credential Manager** (`androidx.credentials`) instead of the deprecated `GoogleSignInClient` for *acquiring* the ID token, but the token is still exchanged the same way — `GoogleAuthProvider.getCredential(idToken, null)` → `signInWithCredential`. So the credential-exchange model is the constant; only the token-acquisition API underneath it has moved (GoogleSignInClient → Credential Manager on native Android; old monolithic `signIn()` → `initialize()`/`authenticate()` in the Flutter `google_sign_in` package — see Q2). Nothing in the fetched docs shows Flutter mobile moving to `signInWithProvider`.

## 2. google_sign_in v7 rewrite

`google_sign_in` **7.0.0** is the breaking rewrite. Per the pub.dev changelog:

- The `GoogleSignIn` instance is now a **singleton**.
- Clients must call and **await `initialize()`** before calling any other method.
- **Authentication and authorization are now separate steps**: `authenticate()` performs sign-in/identity (returns a `GoogleSignInAccount` you read `idToken` off, for Firebase exchange), while `authorize()` is used separately to request additional OAuth **scopes** (e.g. Drive/Contacts access) and obtain access tokens / server auth codes.
- This replaces the old single call `GoogleSignIn().signIn()` that used to hand back both identity and an access token in one shot.

## 3. FlutterFire CLI

- **`lib/firebase_options.dart`**: generated by `flutterfire configure`; contains the non-secret per-platform Firebase config (API key, app ID, project ID, etc.) consumed by `Firebase.initializeApp(options: DefaultFirebaseOptions.currentPlatform)`.
- **Android**: writes `android/app/google-services.json` by default (custom path via a flag for flavor/build-type setups — e.g. `android/app/src/release/google-services.json`). **Unverified against a primary source**: whether the CLI itself edits `android/build.gradle` / `android/app/build.gradle` (or `settings.gradle`) to declare the `com.google.gms.google-services` plugin — the flutterfire_cli README did not confirm this either way in what was fetched; the Firebase Android setup doc (a different, non-FlutterFire flow) shows the plugin declared in the root `build.gradle` `plugins {}` block (`id("com.google.gms.google-services") version "4.5.0" apply false`) plus the app-module `build.gradle` (`id("com.google.gms.google-services")`), which is the current Flutter/Android Gradle DSL location — not `settings.gradle`.
- **iOS**: writes `ios/Runner/GoogleService-Info.plist` by default (custom path via `--ios-out`). The CLI reads the existing bundle ID out of `project.pbxproj` but does not itself edit Xcode project/target settings — per-configuration bundle ID changes (e.g. separate dev/prod schemes) still need manual Xcode edits.
- **Does it replace manual placement?** Yes for the common single-app-per-platform case — `flutterfire configure` both registers the app with the Firebase project *and* downloads/writes the config file to the default path, so there's no separate manual "download from console and drop into folder" step needed. Manual work only returns for non-default flows (multiple flavors/schemes needing per-build-type config files, or per-scheme bundle-ID changes in Xcode).

## 4. Android requirements

- **minSdk**: `google_sign_in` 7.2.0 declares Android SDK **21+**. `firebase_core`'s changelog shows a historical breaking bump ("android plugins require minSdk 21, auth requires minSdk 23" at firebase_core 3.0.0) and `firebase_auth`'s own changelog shows a further breaking bump at firebase_auth 5.0.0 ("Android minimum SDK raised to 23"). I could not get a single current page to restate the exact current-version minSdk number directly (pub.dev's own package page did not surface it in the fetched content), so treat **23** as the effective floor carried forward from the 5.0.0 changelog entry, unless a later breaking-change entry raised it further (not seen in what was fetched).
  - **Repo comparison**: this repo's effective Android minSdk is **24** (confirmed directly from the installed Flutter SDK's `FlutterExtension.kt`, per the repo facts). 24 ≥ 23, so the repo **meets** the firebase_auth/google_sign_in minSdk floor as currently understood. **Unverified**: that 23 is still the current floor as of the latest firebase_auth 6.6.1 — no later changelog entry raising it further was found in the fetched pages, but the fetch was a summarized changelog, not the full raw file.
- **Google Services Gradle plugin location**: root `build.gradle` `plugins {}` block, declared with `apply false`, plus the app-module `build.gradle` applying it without a version — this is the current Android Gradle plugins-DSL convention shown in Firebase's own Android setup doc. Not `settings.gradle`.
- **SHA-1/SHA-256 fingerprints to register in Firebase console**: debug keystore, release keystore, and (if enrolled) the Play App Signing certificate — because Play App Signing re-signs the APK with a Google-held key that differs from your upload key, so the fingerprint Firebase needs to trust for sign-in flows in production is the *app signing* certificate, not your upload certificate.
  - Debug keystore (macOS/Linux): `keytool -list -v -alias androiddebugkey -keystore ~/.android/debug.keystore` (password `android`)
  - Debug keystore (Windows): `keytool -list -v -alias androiddebugkey -keystore %USERPROFILE%\.android\debug.keystore`
  - Release keystore: `keytool -list -v -alias <your-key-name> -keystore <path-to-production-keystore>`
  - All variants at once: `./gradlew signingReport` (prints SHA1/SHA-256/MD5 for every configured variant)
  - Play App Signing certificate: Play Console → your app → Release → Setup → App Integrity, read the SHA-1 there (not derivable from a local keystore once Play App Signing is enabled).

## 5. iOS requirements

- **Minimum iOS deployment target**: `google_sign_in` 7.2.0 declares iOS **12.0+**. `firebase_auth`'s changelog shows a breaking bump to iOS deployment target 13 at firebase_auth 5.0.0. A later changelog line ("bumped iOS SDK to 12.0.0" at what was summarized as firebase_auth/firebase_core 6.0.0/4.0.0) most likely refers to the *Firebase iOS native SDK dependency version number* (12.0.0), not a deployment-target downgrade to iOS 12 — version numbers for the native SDK and the deployment target happen to collide numerically here, and the fetched changelog summary did not disambiguate this cleanly. **Unverified**: I did not get a single authoritative line stating today's exact minimum iOS deployment target for firebase_auth 6.6.1 / firebase_core 4.14.0; treat **13** (from the firebase_auth 5.0.0 breaking-change entry) as the safer floor.
  - **Repo comparison**: this repo's `IPHONEOS_DEPLOYMENT_TARGET` is **15.0**. 15.0 ≥ 13 (and ≥ 12), so the repo **meets** the iOS deployment-target floor under either reading.
- **Info.plist URL scheme**: add a `CFBundleURLTypes` entry whose **URL Schemes** value is the `REVERSED_CLIENT_ID` string copied out of `GoogleService-Info.plist`, added via Xcode's target → Info tab → URL Types → “+”.
- **CocoaPods/Xcode setup**: the fetched Firebase iOS doc for Google Sign-In (`firebase.google.com/docs/auth/ios/google-signin`) currently documents the **Swift Package Manager** path rather than CocoaPods — add the `firebase-ios-sdk` and `GoogleSignIn-iOS` Swift packages via Xcode's File → Add Packages, add `-ObjC` to Other Linker Flags, and copy the downloaded `GoogleService-Info.plist` into the Xcode project, overwriting any existing copy. This doc is for native iOS/Swift, not FlutterFire — FlutterFire's iOS integration still runs through CocoaPods under the hood (`ios/Podfile`) per the standard `flutterfire configure` + `pod install` flow, but I did not find a primary FlutterFire-specific page in this fetch pass spelling out the current Podfile platform-version pin; the general Flutter iOS build config (this repo's `IPHONEOS_DEPLOYMENT_TARGET = 15.0`) is what governs the effective floor for a Flutter app rather than a Podfire-only setting.

## 6. Pre-console-creation decisions

- **Project ID**: permanent once resources are provisioned — *"After Firebase provisions resources for a Firebase project, you cannot change its project ID."* If you want a specific ID (e.g. for a `PROJECT_ID.web.app` hosting subdomain), it must be fixed at creation time. Project **name** (display label), by contrast, can be edited any time.
- **Android package name (applicationId)**: must be decided before/at Android-app registration — Firebase's own Android setup doc states the package name is **case-sensitive** and **cannot be changed for a Firebase Android app after it's registered**. Changing the applicationId later means registering a new Firebase Android app (new `google-services.json`), not editing the existing one.
- **iOS bundle ID**: the search-derived summary of Firebase's project docs suggests more flexibility (e.g. an App Store ID can be added after the fact), but I found no primary-source line explicitly stating the bundle ID itself can be changed post-registration without re-registering — treat bundle-ID immutability as the safer working assumption, symmetric with Android, until a primary source says otherwise. **Unverified.**
- **Android and iOS as separate apps**: confirmed — *"A Firebase project can have one or more Firebase Apps registered to it (for example, both the iOS and Android versions of an app...)"*, all sharing the same project-level backends (Auth, Firestore, etc.). So this repo will end up with two Firebase "app" registrations (one Android, one iOS) inside one Firebase project.
- **`com.example.*` as a real identifier — flag for this repo specifically**: this repo's current identifiers are `com.example.project_tweety` (Android applicationId) and `com.example.projectTweety` (iOS bundle id). Google Play Console is documented elsewhere (outside the primary-source set fetched here) to reject `com.example.*` at publish time for real apps. **Unverified against a primary source in this pass** whether the *Firebase console itself* blocks registering an app with a `com.example.*` package name/bundle id — none of the fetched Firebase docs mention such a block, and nothing suggests Firebase enforces Play's publishing-time namespace rule at registration time. Reasoned inference only: Firebase registration will very likely **succeed** with `com.example.*` (it's just a string identifier to Firebase), but the app **cannot be published** to Google Play under that applicationId later — so the identifier should be changed before Play publishing, and ideally before Firebase registration too, since the Android package name is immutable once registered (see above), meaning a later rename means re-registering a new Android app and re-downloading `google-services.json`.

- Sources:
  - https://firebase.google.com/docs/projects/learn-more
  - https://firebase.google.com/docs/android/setup
  - (Play Console's `com.example.*` publish-time rejection is common Android developer knowledge outside this task's primary-source set — flagged as unverified here per the constraint, not stated as a fetched fact)

## Provisioning checklist

1. **Pick real, final identifiers before touching the Firebase console.** Decide the production Android `applicationId` and iOS bundle id now — not `com.example.*`. Both are effectively immutable after Firebase registration (Android confirmed by primary source; iOS treated the same way pending confirmation). Update:
   - `android/app/build.gradle` → `applicationId "<your.real.id>"`
   - `ios/Runner.xcodeproj/project.pbxproj` → `PRODUCT_BUNDLE_IDENTIFIER = <your.real.id>` (all configs), or via Xcode's target settings UI.
2. **Create the Firebase project** in the Firebase console, fixing the **project ID** now (it cannot be changed later); the project **name** can be edited afterward if needed.
3. **Register the Android app** under that project using the exact `applicationId` chosen in step 1. This creates a distinct Firebase "app" resource from the iOS one, sharing the same project's Auth/Firestore backends.
4. **Register the iOS app** under the same project using the exact bundle id from step 1.
5. **Enable the Google sign-in provider** in Firebase console → Authentication → Sign-in method.
6. **Generate and register Android SHA fingerprints** in Firebase console → Project settings → your Android app → SHA certificate fingerprints:
   - Debug: `keytool -list -v -alias androiddebugkey -keystore ~/.android/debug.keystore` (or `./gradlew signingReport` from the Android project root, which prints every variant at once).
   - Release: `keytool -list -v -alias <key-alias> -keystore <path-to-release-keystore>`.
   - If Play App Signing is/will be enabled: also pull the SHA-1 from Play Console → your app → Release → Setup → App Integrity, and register that one too (it differs from your local release-keystore fingerprint once Play re-signs the app).
7. **Install and run the FlutterFire CLI** from the repo root:
   - `dart pub global activate flutterfire_cli`
   - `flutterfire configure` — select the Firebase project from step 2, select Android + iOS, confirm the applicationId/bundle id match step 1. This writes `lib/firebase_options.dart`, `android/app/google-services.json`, and `ios/Runner/GoogleService-Info.plist`.
8. **Wire up the Android Gradle plugin** if the CLI didn't already: root `android/build.gradle` `plugins {}` block adds `id("com.google.gms.google-services") version "<latest>" apply false`; `android/app/build.gradle` `plugins {}` block adds `id("com.google.gms.google-services")` (no version). Confirm `minSdkVersion` resolves to at least 23 (this repo already resolves to 24 via `flutter.minSdkVersion`, so no change needed here).
9. **Wire up iOS**: add the `REVERSED_CLIENT_ID` value (read out of the freshly generated `ios/Runner/GoogleService-Info.plist`) as a `CFBundleURLTypes` → URL Schemes entry in `ios/Runner/Info.plist` (via Xcode target → Info tab → URL Types, or by hand-editing the plist). Confirm `GoogleService-Info.plist` is added to the Runner target in Xcode (FlutterFire CLI writes the file but doesn't always guarantee Xcode target membership — check "Copy Bundle Resources" for the target). Run `pod install` inside `ios/` after any Podfile-affecting dependency change (adding `firebase_auth`/`google_sign_in` to `pubspec.yaml` triggers this via `flutter pub get` + the next `flutter build`/`flutter run`).
10. **Add the packages** to `pubspec.yaml`: `firebase_core`, `firebase_auth`, `google_sign_in` at their current versions (4.14.0 / 6.6.1 / 7.2.0 respectively as of this check, run `flutter pub get` and let it resolve — don't hand-pin unless a conflict appears).
11. **Implement sign-in using the v7 `google_sign_in` API**: call `GoogleSignIn.instance.initialize(...)` once at startup, then `authenticate()` to get a `GoogleSignInAccount`, read `idToken` off its `authentication`, exchange via `GoogleAuthProvider.credential(idToken: ...)` → `FirebaseAuth.instance.signInWithCredential(...)`. Do not reach for `signInWithProvider`/`signInWithPopup` on mobile — those are web-only per the fetched docs.
12. **Re-run `flutterfire configure`** any time a new platform, new Firebase service, or a changed applicationId/bundle id is introduced — it is not a one-shot command.
